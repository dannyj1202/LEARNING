Style with Emotion

VehicleCard renders real, typed data now. Time to make it look like the reference screenshot instead of unstyled HTML.

Mission tie-in: every lesson so far has been about correctness — the right data, in the right shape, rendered in the right place. Look at the reference screenshot again: none of that work is visible yet. Emotion is how the card border, the price color, and the pill-shaped Book button actually appear.

A styled component is a real component

Official docs: @emotion/styled takes an HTML tag and a template literal of CSS, and returns a React component that renders that tag with that CSS attached. 

import styled from "@emotion/styled";

const Card = styled.article`
  border: 1px solid #e2e2e2;
  border-radius: 8px;
  padding: 1rem;
`;

const BookButton = styled.button`
  background: #0a6e78;
  color: white;
  border-radius: 999px;
  padding: 0.5rem 1.25rem;
  border: none;
`;

function VehicleCard({ title, price }: Vehicle) {
  return (
    <Card>
      <h2>{title}</h2>
      <p>USD {price}</p>
      <BookButton>Book now</BookButton>
    </Card>
  );
}

Card and BookButton are not helpers that apply styling — they are the component. Use them exactly like <article> or <button>, anywhere in your JSX.

Styling from a prop — and typing it

A FilterChip looks different when selected. Emotion lets a prop drive the CSS directly, and — since this is TypeScript — that prop gets a real type, the same way VehicleCard's props do: 

const Chip = styled.button<{ active: boolean }>`
  background: ${(props) => (props.active ? "#0a6e78" : "white")};
  color: ${(props) => (props.active ? "white" : "#1a1a1a")};
  border-radius: 999px;
`;

<Chip active={true}>Meet & Greet</Chip>
Good news first. Official docs: "Emotion passes all props (except for theme) to custom components and only props that are valid html attributes for string tags." A DOM tag like styled.button already filters to real HTML attributes automatically. active isn't a real <button> attribute, so Emotion keeps it off the DOM for you — no extra code needed.

The trap: a prop name that happens to be a real attribute

The filter only knows attribute names, not your intent. If a style-only prop happens to share its name with a genuine (even old, rarely-used) HTML attribute, it passes the filter and lands on the DOM anyway — Emotion's own docs use exactly this case as their example: 

const PriceTag = styled.p<{ color: string }>`
  color: ${(props) => props.color};
`;

<PriceTag color="red">USD 29 (sale!)</PriceTag>
// renders: <p color="red" class="css-xyz">USD 29 (sale!)</p>

color is a genuine, if legacy, HTML attribute (<font color="red">, from way back) — so Emotion's default check treats it as legitimate and forwards it, even though here it's meant purely for styling.

Rule to remember — this one bites in real code review. Rename the prop to something that isn't a real attribute (like highlightColor) and the problem disappears automatically — the default filter keeps non-attribute names off the DOM. If you must keep the colliding name, the documented fix is Customizing Prop Forwarding: 
import styled from "@emotion/styled";
import isPropValid from "@emotion/is-prop-valid";

const PriceTag = styled("p", {
  shouldForwardProp: (prop) => isPropValid(prop) && prop !== "color",
})<{ color: string }>`
  color: ${(props) => props.color};
`;

Note the two changes: styled.p becomes styled("p", { ... }) — the options object only exists on the function-call form, not the dot shorthand — and isPropValid comes from a separate package, @emotion/is-prop-valid. It's the same check Emotion runs internally by default; here you're composing on top of it, not replacing it.

Skill check

Each of these is a small code review. Answer from memory — do not scroll up.

Check 1

const PriceTag = styled.p<{ color: string }>`...`; used as <PriceTag color="red">USD 29</PriceTag> — does color end up as an attribute on the rendered <p>?

Check 2

Same idea, renamed: styled.p<{ highlightColor: string }>, used as <PriceTag highlightColor="red">USD 29</PriceTag> — does highlightColor leak onto the DOM?

Check 3

You must keep the prop named color (API consistency with other components). What's the actual documented fix to stop it leaking onto the DOM?
