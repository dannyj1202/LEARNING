Object types and structural typing

Why does a fresh { ...seats: 7 } get flagged, but the exact same value passed through a variable doesn't? The answer is the single most useful "why did TypeScript accept/reject this?" mental model there is.

Mission tie-in: in Lesson 0004 you learned an extra field on a Vehicle literal gets flagged. That's true, but incomplete — and the missing piece is exactly the kind of thing a reviewer needs to know cold, because it looks identical on the surface and behaves differently underneath.

TypeScript checks shape, not name — "duck typing"

TypeScript uses a structural type system: if a value has all the properties a type requires, it's accepted — regardless of what the value was declared as, or whether it was ever labeled with that type's name at all. 

interface Point {
  x: number;
  y: number;
}

function printPoint(p: Point) {
  console.log(`${p.x}, ${p.y}`);
}

const myObject = { x: 10, y: 20, z: 30 }; // never declared as Point, has an extra field
printPoint(myObject); // fine — it HAS the required shape

Source: TypeScript Field Guide, §1.2 — "if it walks like a duck and quacks like a duck, TypeScript treats it as a duck — regardless of what it's named." This is different from languages like Java or C#, which check by declared class name, not shape.

So why did the extra field get flagged in Lesson 0004?

Compare these two, side by side — same extra field, different outcome: 

// A) Fresh literal, assigned directly — TypeScript flags "seats"
const a: Vehicle = { id: "v4", title: "Minivan", price: 74, seats: 7 };

// B) Same value, passed through a variable first — TypeScript allows it
const raw = { id: "v4", title: "Minivan", price: 74, seats: 7 };
const b: Vehicle = raw; // no error — myObject-style structural match
Rule to remember. Excess property checks only apply to fresh object literals written directly where a type is expected. The moment that same value passes through a variable, TypeScript falls back to pure structural matching: "does it have everything Vehicle needs?" — extra fields stop being an error. This isn't a loophole to exploit; it's why the check exists at all — to catch literal typos, not to police every object that happens to have extra data.

Optional and readonly fields

Two modifiers show up constantly on real object types: 

interface Vehicle {
  readonly id: string;      // cannot be reassigned after creation
  title: string;
  price: number;
  discountCode?: string;    // optional — may be present or absent, never null
}

? means the property can be omitted entirely — not set to undefined explicitly, just left out. readonly means the property can be read but never reassigned once the object exists, independent of whether the whole object itself is const — handy for an id, which should never change after a vehicle is created.

type vs interface — a real decision

Both can describe Vehicle's shape. The difference that actually matters day to day:

  • interface can be extends-ed cleanly and merged/re-opened by libraries — the production default for object shapes, especially component props.
  • type is required for unions ("loading" | "success"), tuples, and function types like SortFn from Lesson 0004b — interface can't express those.

Source: TypeScript Field Guide, §1.8 — "Most teams default to interface for object shapes... Reach for type when you need unions, tuples, or advanced type manipulation."
