1. interface — and why this repo uses both

You already know type from Lesson 0004. Here's the thing that confuses people opening this repo: filters.types.ts is entirely interface, and home-page.types.ts is entirely type — same package, same week, both styles. 

// filters.types.ts
export interface PriceFilterData {
  min: number;
  max: number;
}

// home-page.types.ts
export type HomePageSnapshot = {
  flow: TransportFlow;
  passengers: number;
};
For reading purposes, these are the same thing. Both describe an object shape; both are erased at compile time. The differences (interface can be re-opened and extends-ed; type can express unions and tuples, which interface cannot) only matter when you're writing one. When you're reading, treat interface X { and type X = { as interchangeable and move on.

Source: TypeScript Field Guide, §1.8 — "Consistency matters more than the specific choice." Worth noting in review: this repo isn't consistent, so don't read meaning into which one a file picked.

2. T[] — an array of a named type

A [] after any type means "a list of those." It composes with the names you've already defined: 

export interface FilterData {
  price: PriceFilterData;      // exactly one
  city: CityFilterItem[];      // a list of them
  tag: TagFilterItem[];
  cancellation: toggleFilterItem;
}

Read city: CityFilterItem[] as "the city key holds an array, and every element in it must have the CityFilterItem shape." This is how the whole filter sidebar is described in one screen of code. (Field Guide §1.4.)

3. A type can refer to itself

The last interface in filters.types.ts does something that looks illegal the first time you see it: 

export interface CategoryFilterItem {
  id: number;
  totalCount: number;
  selected?: boolean;
  hasSubCategories: boolean;
  categories?: CategoryFilterItem[];  // ← itself
}

That's a recursive type, and it's completely valid. It's how a category filter models nesting to any depth: a category may contain categories, which may contain categories. The ? is what stops it being infinite — a leaf category simply omits categories.

4. Unions — string | null

The | reads as or. A union says the value may be any one of the listed types. transport.types.ts is full of them: 

export interface BookingLocation {
  id: string;                              // must be a string
  city?: string | null;                    // string, null, or absent
  terminals?: AirportSearchTerminal[] | null;
}

? and | null answer two different questions, and this is the distinction that trips up every reviewer new to the file:

Written Legal values
city: string A string. The key must be present.
city?: string A string, or the key is left out entirely.
city: string | null A string or null. The key must still be present.
city?: string | null A string, null, or left out. Three states.

Look at Destination vs BookingLocation in the real file: Destination.city is string, but BookingLocation.city is string | null. That difference is the author telling you the API can hand back an explicit null on one and not the other — signal worth reading, not noise.

The landmine: this repo has strict: false

Everything above describes what those annotations mean. Here is what the compiler actually enforces in ct-web-transport — and they are not the same thing. 

// packages/sdk/tsconfig.json  AND  packages/app/tsconfig.json
"strict": false,

strict: false leaves strictNullChecks off, and the official docs are blunt about the consequence: null and undefined are "effectively ignored by the language… This can lead to unexpected errors at runtime."

I ran this through the repo's own TypeScript (4.9.5) to confirm rather than assume:

function label(loc: BookingLocation) {
  return loc.city.toUpperCase();   // city is `string | null`
}

$ tsc --noEmit --strict false probe.ts
exit=0                             ← compiles clean

$ tsc --noEmit --strict true  probe.ts
probe.ts(9,10): error TS18049: 'loc.city' is possibly 'null' or 'undefined'.
The review rule. In this repo, the type files tell you the truth about shape but the compiler will not enforce nullability. A | null or a ? is a note from the author to you — not a guardrail. So when you review a diff that reads loc.city.toUpperCase() and the type says string | null, that is a real crash waiting, and nothing but a human will catch it. That is your job on this codebase.

Don't over-correct, though — strict: false does not mean "checking is off." Verified with the same compiler, all four of these still error: a missing required property, a string where a number belongs, an unknown extra key on a fresh literal (the excess property check from Lesson 0004c), and a wrong element type in an array. Only the null/undefined checking is switched off. (Field Guide §4.1 lists exactly which flags strict bundles.)

5. The barrel — export * from

// packages/sdk/src/types/index.ts — the entire file
export * from './api';
export * from './filters.types';
export * from './home-page.types';
export * from './sort.types';
export * from './transport.types';

export * from './x' re-exports everything x exports, as if this file had declared it. Five lines collapse four files into one import surface, which is why App code writes one import from the package root instead of four deep paths. The @/ you see in import type { Airport } from '@/types/transport.types' is a path alias, configured in tsconfig.json ("paths": { "@/*": ["./*"] }) — it means "from this package's src," not a node_modules package.
