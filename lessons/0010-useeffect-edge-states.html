useEffect — and the states nobody designs

After filters work, real pages still need loading, empty, and “no matches for these filters.” Some of that is just conditional JSX. Some of it needs an effect — code that syncs React with something outside React. Knowing when an effect is the wrong tool matters as much as knowing the API.

Mission tie-in: side-project task 0009. File number is 0010 (lesson 0009 is lift-state). Your vehicle page should show honest empty/loading UI before Next.js routing polish.

Three UI states (no Effect required)

State Typical condition What to render
Loading isLoading === true Skeleton / “Loading rides…”
Empty catalog vehicles.length === 0 “No vehicles available”
No matches data exists, visible.length === 0 “No rides match these filters” + clear filters

“No matches” is just derived data after lift-state — an if in JSX, not an Effect. Official guidance: You Might Not Need an Effect.

What useEffect is for

Effects synchronize with an external system — network, browser APIs, a non-React widget — after React has painted. Synchronizing with Effects. 
useEffect(() => {
  let cancelled = false;
  setIsLoading(true);
  fetchVehicles().then((data) => {
    if (!cancelled) {
      setVehicles(data);
      setIsLoading(false);
    }
  });
  return () => { cancelled = true; }; // cleanup if unmounted
}, []); // run after mount (dependency array)

When Effect is the wrong tool

  • Transforming data for render (filter/sort) → calculate during render.
  • Resetting state when a prop changes → often key the component or calculate instead.
  • Chaining setState in an Effect just because another state changed → usually derive or update together in the event handler.

A fair code-review question: “Does this Effect talk to the outside world, or is it recreating props/state React already has?”
