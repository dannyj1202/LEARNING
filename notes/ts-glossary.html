Read this section firstType-level vs. value-level

Every one of your unfamiliar constructs traces back to this one distinction. TypeScript files hold two layers stacked on top of each other: values — the actual variables, functions, and objects that exist while the code runs — and types — descriptions the compiler uses to catch mistakes, which disappear entirely before your code ever reaches a browser. That disappearing act is called erasure.

Written in the file What survives to the running browser
import type { ReactNode } from 'react'; Nothing. The whole line is deleted at compile time.
export type Props = { ... }; Nothing. type never exists past compilation.
textColor?: COLOR_VARIANTS Nothing of the annotation. Only the property itself, if a caller actually passes one.
: JSX.Element, : void Nothing. Return-type annotations are compiler-only.
export enum COLOR_VARIANTS { WHITE = 'white', ... } A real JavaScript object — { WHITE: 'white', ... } — that exists at runtime. Enums are the exception.

Worth pausing on

Almost everything with a "type flavor" — type, interface, import type, every : X annotation — is erased. enum quietly breaks that pattern: it looks like a type-only declaration but the compiler actually emits a real object for it. That's confirmed straight from the design system's source (theme/palette.theme, theme/typography.theme) — both COLOR_VARIANTS and TYPOGRAPHY_VARIANT are declared with export declare enum, so your instinct on those two was exactly right.

Line by line

L1

import type — pulls in a name usable only in type position. The whole line is deleted at compile time; nothing of it reaches the browser.

L2

A regular import, by contrast, survives to runtime. Typography is a real component and COLOR_VARIANTS is a real object — both exist while the page runs.

L5–14

The repo convention: an exported Props type sitting directly above the component it describes. That's a house style, not a TypeScript requirement.

L8

textColor? — the ? makes the property optional. Callers may leave it out.

L9–13

A nested object type, written inline rather than pulled out into its own name. Every field inside is independently optional.

L16

Three things at once: the parameter is destructured ({ icon, text, ... }), the whole parameter is typed : Props, and the function is declared to return : JSX.Element — a piece of renderable React markup.

L17

Destructuring with defaults. If stylingSettings is missing, || {} substitutes an empty object so the destructuring doesn't throw — then each of iconSize, textSize, gap falls back to its own default. This is plain JavaScript; no TypeScript involved.

L19–20

{{ gap }} is not special syntax — the outer braces are JSX's “expression goes here,” the inner ones are an object literal. So it reads style={ an object }.

Line by line

L6–11

The author grouped the imports by hand: utilities, then types. Note that only the // types group uses import type — those two lines vanish at compile time, the rest don't.

L16

onFilterChange: () => void — a function-typed property. It means “this prop must hold a function that takes no arguments and hands nothing back.” This is how a child says “something changed” without knowing what the parent will do.

L22

: void on a return means “don't expect a usable value back.” The function still does things — it just doesn't produce a result worth capturing.

L29

_map is lodash's version of .map() — same idea as Lesson 0003. The callback's parameters are explicitly typed (item: TransportFilterSelectableItem, index: number), which is how you learn the element type without opening the SDK.

L30

key={item.key} — a stable id, not the array index. Exactly the rule from Lesson 0003. The index is also in scope here, which makes the choice deliberate.

L30

$first and $last are Emotion transient props (Lesson 0005) — the $ prefix marks them as styling-only, so they're used to compute CSS and never forwarded onto the DOM element.

L36

onChange={() => handleToggle(item.key)} — wrapped in an arrow function because the handler needs an argument. Writing onChange={handleToggle(item.key)} would call it immediately during render instead of on click. Common review catch.

Group AShaping data

How these files describe "what shape of object am I allowed to pass here."

type aliastype-level

A name you give to a shape, so you can write the name instead of the whole shape every time. type Props = {...} means "from now on, Props is this exact object shape." 

export type Props = {
  icon: ReactNode;
  text: string;
  textColor?: COLOR_VARIANTS;
  ...
};

Every component in these three files exports a Props type right above the component itself — that's the repo's convention, not a TypeScript requirement.

optional property ?type-level

Inside an object type, a ? right after a property name means "callers may leave this out entirely." Without it, leaving the property out is a compile error.

textColor?: COLOR_VARIANTS;
stylingSettings?: { ... };

Don't confuse this with ?. below — same character, two unrelated jobs. This one lives inside a type; ?. lives inside an expression, at runtime.

nested object typetype-level

An object type can contain another object type inline, instead of pulling it out into its own named type. Every field inside can be optional independently.

stylingSettings?: {
  iconSize?: number;
  textSize?: TYPOGRAPHY_VARIANT;
  gap?: number;
};

Reads the same way you'd read a plain JS object literal — TypeScript object types intentionally mirror JS object syntax.

function-typed propertytype-level

() => void as a property's type means "this property must hold a function that takes no arguments and returns nothing usable" — i.e. a callback.

export type Props = {
  ...
  onFilterChange: () => void;
};

Appears in every filter component's Props in this repo — it's how a child tells a parent "something changed," without knowing what the parent does about it.

Group BEnums — the odd one out

Confirmed directly from @tajawal/ct-web-design-system's compiled types.

enumtype + runtime

A fixed, named set of allowed values — callers pick one member instead of typing an arbitrary string, so a typo like "withe" is caught at compile time instead of failing silently in the UI.

export declare enum COLOR_VARIANTS {
  MINESHAFT = "mineshaft",
  WHITE = "white",
  /* ...61 more */
}

Used both as a type (textColor?: COLOR_VARIANTS in InfoRow.tsx:8) and as a value (TYPOGRAPHY_VARIANT.CAPTIONREG in InfoRow.tsx:17) — the same name works in both worlds, which is exactly what makes enums the exception to erasure above.

enum member as a valueruntime

Because the enum compiles to a real object, TYPOGRAPHY_VARIANT.CAPTIONREG isn't just a type — it's an actual string ("captionReg") you can hand to a default parameter, log, or compare with ===.

const { textSize = TYPOGRAPHY_VARIANT.CAPTIONREG } = stylingSettings || {};
...
variant={
  isDesktop ? TYPOGRAPHY_VARIANT.HEADING3SEMBLD : TYPOGRAPHY_VARIANT.HEADING2
}

The ternary in MultiSelectFilter is a plain JS ternary — nothing TS-specific about it — it's just choosing between two runtime values that happen to come from an enum.

Group CFunctions: what goes in, what comes back

: voidtype-level

"This function doesn't hand back a usable value." It can still do things (mutate, call other functions) — it just promises nothing worth capturing in a variable. 

function handleToggle(key: string): void {
  filter.toggle(key);
  onFilterChange();
}

Contrast with a function that promises a real value back, e.g. one typed : number or : boolean — the return type is the function's contract with whoever calls it.

: JSX.Elementtype-level

A built-in type meaning "a piece of renderable React markup." Same annotation slot as : void above — just promising a different kind of thing back.

export default function InfoRow({ icon, text, ... }: Props): JSX.Element {
  return ( /* ... */ );
}

Every default-exported component function in these three files ends its signature with this — it's the repo's standard for "this is a component."

default value in destructuringruntime (JS)

Plain JavaScript, not TypeScript — when you pull a property out of an object and it's undefined, the = value fills in a fallback instead.

const { iconSize = 16, textSize = TYPOGRAPHY_VARIANT.CAPTIONREG, gap = 8 }
  = stylingSettings || {};

The || {} at the end matters too: if stylingSettings itself was never passed, this destructures an empty object instead of crashing on undefined.

default parameter valueruntime (JS)

Same idea, one level up — a whole parameter gets a fallback if the caller doesn't pass it, right in the function signature.

function MultiSelectFilter({ ..., isDesktop = false }: Props): JSX.Element {

This is exactly why isDesktop is marked optional (isDesktop?: boolean) in the Props type above it — the type says "may be omitted," the default value says "here's what happens when it is."

Group DThe import boundary

import typetype-level

A version of import that only pulls in type information — never a real, runtime value. Straight from the erasure idea above: since types don't exist once compiled, the compiler can strip this entire line out of the bundle.

// types
import type { PolicyFilter } from '@tajawal/web-transport-sdk/stores';
import type { TransportFilterSelectableItem } from '@tajawal/web-transport-sdk/types';

Notice the file groups imports by comment: regular imports, then # utils, then # types last, using import type for that whole group. That grouping is a repo convention worth copying.

regular import (contrast)runtime

A normal import pulls in something the code actually calls or renders while running — it cannot be erased, because the browser needs it.

import { Typography } from '@mui/material';
import { Toggle, TYPOGRAPHY_VARIANT } from '@tajawal/ct-web-design-system';
import { buildTestId } from '@tajawal/web-common/lib';

TYPOGRAPHY_VARIANT is imported here as a normal import, not import type — because (per Group B) it's used as a real value, not just a type.

Group ETwo operators you'll see constantly

Not TypeScript-specific — both are plain JavaScript — but they show up everywhere once a codebase starts being strict about what might be missing. Cited from VehicleCard.tsx, a fourth real file, since neither appears in the original three.

optional chaining ?.operator

"Access this, but if the thing on the left is null or undefined, stop right there and give back undefined instead of throwing." 

priceDetail.discount.type?.toLowerCase().includes('percent')
priceDetail?.discount?.value

Chainable — the second example checks priceDetail and discount independently, so a missing value at either step stops the chain instead of crashing.

nullish coalescing ??operator

"Use the left value, unless it's specifically null or undefined — then use the right one." 

discountedPrice={priceDetail.originalPrice ?? undefined}

Different from ||, which also overrides valid falsy values like 0 or "". See the self-check below — this distinction is the single most common source of a subtle bug.

Group FThe SDK type files

Everything above came from component files. These came from the four type files in packages/sdk/src/types/ — sort.types.ts, filters.types.ts, transport.types.ts, index.ts — which is where the repo defines what a "ride" actually is. Taught in Lesson 0006.

interfacetype-level

Another way to name an object shape. For reading purposes it is interchangeable with type X = {...} — both describe a shape, both are erased at compile time.

export interface PriceFilterData {
  min: number;
  max: number;
}

This repo uses both — filters.types.ts is all interface, home-page.types.ts is all type. Don't read meaning into which one a file picked; the choice isn't consistent here. The real differences (interface can be re-opened and extends-ed; only type can express a union) matter when writing, not reading.

array type T[]type-level

[] after any type means "a list of those." Read city: CityFilterItem[] as "the city key holds an array, and every element in it must have the CityFilterItem shape."

export interface FilterData {
  price: PriceFilterData;   // exactly one
  city: CityFilterItem[];   // a list
  tag: TagFilterItem[];
}

The entire filter sidebar's data shape fits on one screen because of this — named shapes composed into lists, rather than one giant nested literal.

recursive typetype-level

A type is allowed to refer to itself. Valid, not a mistake — it's how you model nesting to an unknown depth.

export interface CategoryFilterItem {
  id: number;
  hasSubCategories: boolean;
  categories?: CategoryFilterItem[];
}

A category may contain categories, which may contain categories. The ? is what keeps it finite — a leaf category just omits the key.

union type |type-level

| reads as or: the value may be any one of the listed types. In these files it's almost always used to add null.

placeId?: string | null;
terminals?: AirportSearchTerminal[] | null;

Unions can hold any types, not just null — a union of exact strings ('loading' | 'success') is the safer alternative to string. You haven't hit one in this repo yet, but you will.

path alias @/build-level

A prefix configured in tsconfig.json that stands in for a directory — not a package in node_modules.

// tsconfig.json
"baseUrl": "./src",
"paths": { "@/*": ["./*"] }

// so this means src/types/transport.types
import type { Airport } from '@/types/transport.types';

First instinct on seeing @/ is "scoped npm package" (like @tajawal/…). It isn't. One @ is a scope, @/ is this package's own src.

Group GNullability — and the repo's landmine

? and | null answer two different questions. Read together they describe three legal states, and in this repo the compiler enforces none of them.

Written in the file Values the annotation allows
city: string A string. The key must be present.
city?: string A string, or the key left out entirely.
city: string | null A string or null — but the key must still be present.
city?: string | null A string, null, or left out. Three states.

Both spellings appear side by side in transport.types.ts: Destination.city is string, BookingLocation.city is string | null. That's the author signalling the API can return an explicit null on one and not the other — signal worth reading, not noise.

The landmine — verify this yourself before trusting any nullability annotation here

Both packages/sdk/tsconfig.json and packages/app/tsconfig.json set "strict": false, which leaves strictNullChecks off. Per the official docs, that means null and undefined are "effectively ignored by the language… This can lead to unexpected errors at runtime." Confirmed by running the repo's own TypeScript 4.9.5: loc.city.toUpperCase() on a string | null compiles clean under --strict false, and fails with TS18049: 'loc.city' is possibly 'null' or 'undefined' under --strict true.

So: the type files tell the truth about shape, but the compiler does not enforce nullability. A | null here is a note from the author to you, not a guardrail. Catching an unguarded access is a human reviewer's job on this codebase.

Don't over-correct — strict: false is narrower than it sounds. Verified with the same compiler, these all still error: a missing required property (TS2741), a string where a number belongs, an unknown extra key on a fresh object literal, and a wrong element type inside an array. Only the null/undefined family is off.

Active recallQuick self-check

Answer in your head first, then open each to check. If one surprises you, that's the one to reread above.

In textColor?: COLOR_VARIANTS, what happens if a caller of InfoRow doesn't pass textColor at all?
Nothing breaks. ? means the property is allowed to be absent — inside the component, textColor is simply undefined. It would only be a compile error without the ?.
Which of these two lines still exists somewhere in the JavaScript the browser actually runs: import type { ReactNode } from 'react'; or export enum COLOR_VARIANTS {...}?
Only the enum. import type is erased completely; the enum compiles into a real object. This is the exception from the erasure table above — worth memorizing since it's counterintuitive.
handleToggle(key: string): void — if you wrote const x = handleToggle('a'), could you usefully do anything with x afterward?
No. TypeScript will let you write it, but x is undefined — void is the function's way of saying "don't expect a return value," so nothing meaningful is there to use.
If priceDetail.originalPrice is 0, what does priceDetail.originalPrice ?? undefined evaluate to?
0 — not undefined. ?? only falls through on null/undefined, and 0 is neither. If this had used || instead, a legitimate price of 0 would have been incorrectly replaced.
terminal?: string | null — how many distinct legal states does that describe, and what are they?
Three: a string, an explicit null, or the key left out entirely. The ? buys "may be absent"; the | null buys "may be present but null." They stack rather than overlap.
A diff adds return loc.city.toUpperCase(); where city is typed string | null. Does CI catch it?
No. strict: false in both packages means strictNullChecks is off, so the compiler ignores the | null completely — it builds, ships, and throws the first time the API returns a null. This is a review comment only a human can leave on this repo.
Since strict is off, does const c: CityFilterItem = { id: 1 } — missing the required totalCount — compile?
No — TS2741: Property 'totalCount' is missing. Shape checking is completely unaffected by strict: false; only the null/undefined checks are disabled. Don't let the landmine above talk you into distrusting the types entirely.
categories?: CategoryFilterItem[] sits inside CategoryFilterItem. Is that a mistake?
No — it's a recursive type, and it's the point: a category may contain sub-categories to any depth. The ? is what makes it terminate, since a leaf category simply omits the key.

Definition of doneStill fuzzy — on purpose, for now

Nothing here appeared in the three files this glossary is built from, so rather than force an example that isn't real, they're named and deferred honestly. You'll meet all three soon.

generics — <T>

A way to write one function or type that works across many shapes while still keeping them distinct — e.g. "this returns an array of whatever type went in." You'll likely meet this first in a shared SDK utility or a generic API-response type.

discriminated unions / narrowing

A pattern where an object type has a shared "tag" field (like kind: 'a' | 'b'), and checking that field with an if lets TypeScript automatically figure out the rest of the object's shape inside that branch.

utility types — Partial<T>, Pick<T, K>, Omit<T, K>

Built-in helpers that build a new type out of an existing one — "all of Props but optional," or "only these two fields of Props." Common once a codebase has enough shared types worth reshaping instead of retyping.
